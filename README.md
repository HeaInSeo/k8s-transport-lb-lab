# k8s-transport-lb-lab

## 서버는 3개인데, 왜 한 곳만 일할까?

서버를 3개 띄웠다고 요청도 자동으로 3등분되는 것은 아닙니다.
이 저장소는 **HTTP와 gRPC의 연결 방식을 바꾸고, 어느 서버가 몇 번 일했는지 직접 확인하는 작은 실험실**입니다.

**코드를 읽지 않아도 됩니다. GitHub에서 실행하고, 설명이 붙은 결과 보고서를 읽으면 됩니다.**

[실행 화면 열기](https://github.com/HeaInSeo/k8s-transport-lb-lab/actions/workflows/lab.yml) · [용어를 처음 접한다면](docs/START_HERE.ko.md) · [실험의 정확한 판정 기준](docs/EXPERIMENTS.ko.md)

> 이것은 학습·동작 확인용 실험입니다. HTTP와 gRPC 중 어느 것이 더 빠른지 순위를 매기거나, 운영 환경의 최대 처리량을 보장하는 도구가 아닙니다.

## 1. 가장 편하게 해보기 — 내 컴퓨터에 설치하지 않기

실험은 GitHub가 제공하는 실행 환경에서 진행됩니다. 내 컴퓨터에 Kubernetes나 Docker를 설치할 필요가 없습니다.

1. 위의 **실행 화면**에서 **Run workflow → Run workflow**를 누릅니다. 실행 권한이 있는 계정이 필요합니다.
2. 만들어진 실행 항목을 열고 완료 결과를 확인합니다. **Summary**에 설명형 보고서가 나옵니다.
3. 브라우저에서 더 편하게 읽으려면 같은 화면 아래 **Artifacts → transport-lab-report**를 받습니다. 압축을 모두 풀고, 실행 시각 폴더 안의 **`index.html`**을 엽니다.

HTML 보고서는 인터넷 없이도 열립니다. 먼저 **‘이것만 보기’ → ‘왜 이런 결과가 나왔을까?’** 순서로 읽으면 됩니다.
로그를 처음부터 끝까지 읽을 필요는 없습니다. 실패한 경우에만 해당 실험의 상세 기록과 원본 로그를 확인하세요.

기존 실행 결과를 읽기만 할 때는 다시 실행하지 않아도 됩니다. 아티팩트 보관 기간은 14일입니다.
소스를 `main`에 올리거나 Pull Request를 만들 때도 자동 검증이 실행됩니다.

## 2. 무엇을 하는 실험인가요?

실험용 서버 **Pod 3개**를 만들고, 클러스터 안의 클라이언트가 네 가지 방식으로 요청을 보냅니다.
기본값은 **방식마다 측정 요청 600번**, 총 2,400번입니다. 각 서버는 HTTP와 gRPC를 함께 제공하므로 같은 Pod 배치에서 비교합니다.

**TCP 연결은 ‘전화 걸기’, 요청은 ‘통화 중 질문하기’**라고 생각하면 쉽습니다.
한 번 전화해서 질문을 600번 하는 것과, 질문할 때마다 새로 전화하는 것은 다릅니다.

아래는 **확인하려는 예상 동작**입니다. 실제 측정값은 각 실행의 보고서에 나옵니다.

| 실험 | 전화로 비유하면 | 확인하려는 모습 |
|---|---|---|
| HTTP — 매번 새 연결 | 질문할 때마다 다시 전화하기 | 여러 Pod가 나눠 처리 |
| HTTP — 연결 하나 재사용 | 한 통화에서 계속 질문하기 | 같은 Pod가 전부 처리 |
| gRPC — 기본 Service | 기본 대표번호로 연결해서 계속 질문하기 | 같은 Pod가 전부 처리 |
| gRPC — Headless + round_robin | 상담원별 번호로 각각 연결해 번갈아 질문하기 | 여러 Pod가 나눠 처리 |

**한 Pod가 전부 처리했다고 무조건 실패가 아닙니다.** 두 번째와 세 번째는 한 연결이 한 Pod에 머무는 현상을 확인하는 대조 실험입니다.

마지막 실험에서 Headless는 **Pod들의 주소를 찾도록** 해주고, round_robin은 **gRPC 클라이언트가 호출할 서버를 번갈아 고르도록** 합니다.
클라이언트 프로그램을 3개 만드는 것이 아닙니다. 하나의 gRPC `ClientConn`이 여러 실제 TCP 연결을 관리합니다.

## 3. 보고서는 어떻게 읽나요?

보고서의 앞부분에는 긴 Pod 이름 대신 **Pod A·B·C**와 처리 횟수가 나옵니다. 같은 글자는 그 보고서 안에서 같은 서버를 뜻합니다.

각 실험은 **알아보려던 것 → 시험 방법 → 실제 결과 → 동작 원리 → PASS 기준 → 이번 판정** 순서로 설명합니다.
측정값과 예상 동작을 구분하므로, 실패한 실행을 성공한 것처럼 설명하지 않습니다.

| 보고서에서 보이는 말 | 쉽게 읽으면 |
|---|---|
| **전체 PASS** | 네 실험과 환경 검증이 각각의 기준을 충족했습니다. 전부 균등 분산됐다는 뜻은 아닙니다. |
| **오류 0건** | 오류로 집계된 측정 요청이 없다는 뜻입니다. 준비 실패로 요청을 못 보냈을 수도 있으므로 성공·계획·미실행 수도 함께 봅니다. |
| **TCP 전체** | 준비 단계부터 새로 만든 성공 연결의 누적 개수입니다. 동시에 열린 연결 수가 아닙니다. |
| **측정 중 신규 TCP 0개** | 준비 때 만든 연결을 그대로 썼을 수 있습니다. 요청을 안 보냈다는 뜻은 아닙니다. |
| **p50 / p95 / p99** | 성공한 요청의 응답 시간을 빠른 순서로 놓았을 때 약 50%·95%·99% 지점입니다. 평균이나 최대값은 아닙니다. |
| **미검증** | 실패했다는 뜻이 아니라, 아직 그 조건으로 시험하지 않았다는 뜻입니다. |

예를 들어 **p95가 0.240ms라면 성공 요청의 약 95%가 그 시간 이내에 끝났다는 뜻**입니다.
이 숫자는 읽는 법을 설명하는 예시이며, 현재 실행 결과를 대신하는 값이 아닙니다. 1ms는 0.001초입니다.

긴 실제 Pod 이름, 준비 호출 수, 소스 커밋과 이미지 버전은 보고서 아래의 **상세 기록**을 펼치면 확인할 수 있습니다.
과거 실행의 보고서를 새 형식으로 다시 만들어도, 측정 시각과 측정 당시 소스 커밋은 바꾸지 않습니다.

## 4. kind와 kindnetd는 여기서 무엇을 하나요?

| 이름 | 맡은 일 |
|---|---|
| **kind** | 컨테이너로 작은 Kubernetes 연습장을 만듭니다. |
| **kindnetd** | 연습장 안에서 Pod끼리 통신할 수 있도록 네트워크를 구성합니다. kind의 기본 구성에 포함됩니다. |
| **kube-proxy** | 이번 기본 구성에서 Service로 들어온 TCP 연결을 Pod로 전달하는 규칙을 만듭니다. |
| **gRPC 클라이언트의 round_robin** | 마지막 실험에서 준비된 서버 연결 사이에 호출을 나눕니다. |

**kindnetd가 HTTP/gRPC 요청을 읽고 분배하는 것은 아닙니다.** Pod 사이의 길을 만드는 일과, 요청을 어느 Pod로 보낼지 고르는 일을 구분하는 실험입니다.
기본 실행에는 Cilium, Envoy, 서비스 메시, 인증서 설치가 필요하지 않습니다.

## 5. 지금 확인하는 것과 아직 확인하지 않는 것

지금 확인하는 것은 **서버 3개가 정상적으로 유지되는 동안, 연결 방식에 따라 요청 분포가 어떻게 달라지는가**입니다.
서버들이 두 Kubernetes 노드 이상에 배치됐는지도 확인하지만, kind의 노드는 컨테이너이므로 물리 서버 두 대에서 시험했다는 뜻은 아닙니다.

| 아직 시험하지 않은 조건 | 남은 질문 |
|---|---|
| 서버를 3개에서 5개로 늘리기 | 새 서버를 발견하고 요청을 보내기까지 얼마나 걸릴까요? |
| 서버 하나를 종료하기 | 몇 번 실패하고 언제 복구될까요? |
| 긴 gRPC 스트림 | 이미 진행 중인 통신과 새 통신의 분산은 어떻게 달라질까요? |
| mTLS / Envoy / Cilium / nftables | 보안·프록시·네트워크 구성을 바꿔도 같은 결과가 나올까요? |

**기본 실험의 PASS는 위 조건들까지 검증했다는 뜻이 아닙니다.** 현재는 암호화하지 않은 개발용 통신을 사용합니다. 운영 보안 구성으로 그대로 사용하면 안 됩니다.
HTTP/2 일반 HTTP 대조군, 동시 요청 증가, 기존 gRPC 툴킷 연동도 후속 범위입니다.
구현 여부는 [단계별 확장 계획](docs/ROADMAP.md)에 구분해 두었습니다.

<details>
<summary>로컬 실행 준비물과 명령 보기</summary>

현재 공개 버전에서 검증한 자동 실행 경로는 **Docker 기준**입니다.
kind 자체의 Podman 지원 여부와 별개로, 이 저장소의 Podman 실행 경로는 아직 공개 버전의 검증 완료 범위가 아닙니다.

준비물은 Linux 또는 macOS, 실행 가능한 Docker, `kubectl`, Python 3.9 이상, `make`, `kind`입니다.
Docker 메모리는 6 GiB 이상을 권장하며, 작업 디스크는 여유 공간 8 GiB 이상을 확인합니다.
데모의 Go 빌드는 컨테이너 안에서 하므로 호스트에 Go를 따로 설치하지 않아도 됩니다.

```bash
git clone https://github.com/HeaInSeo/k8s-transport-lb-lab.git
cd k8s-transport-lb-lab
make install-kind   # 이 저장소 안에 고정 버전 설치. 시스템 kind는 바꾸지 않음
make doctor         # 실행 준비 상태 확인
make demo           # 클러스터 생성 → 서버 배포 → 네 가지 실험 → 보고서 생성
```

끝나면 `reports/latest/index.html`을 브라우저로 엽니다.

```bash
make smoke          # 이미 만든 환경에서 다시 측정
REQUESTS=1200 make smoke  # 실험마다 측정 요청을 1,200번으로 변경
make clean          # 이 저장소가 만든 클러스터만 삭제. 보고서는 보존
make ci             # 개발자용 검사. 호스트 Go 필요
```

로컬 자원이 부족하면 다른 파일을 지우거나 서버 설정을 바꾸기보다 GitHub 실행 경로를 이용하세요.

## 7. 공개 범위와 실험 자료

공개하는 것은 일반적인 실험 코드, 재현 방법, 격리된 실험 환경에서 검토한 결과입니다.
**실제 내부 서버 주소·계정·NFS 경로·마운트 설정·인증정보·개인키·kubeconfig는 공개 자료가 아닙니다.**
로컬 실행 자료는 자동으로 GitHub에 올라가지 않습니다. 진단 파일을 수동으로 공유하기 전에도 내용을 검토해야 합니다.
보고서에는 허용한 버전 식별값만 표시하며 원본 환경 로그 전체를 그대로 붙이지 않습니다. 이것이 모든 진단 파일의 자동 비식별화를 보장하지는 않습니다.

기존 애플리케이션의 업무 코드나 서비스 계약을 옮기지 않습니다. gRPC 측정에는 표준 `Health/Check` 단항 호출을 사용합니다.
다른 클러스터를 건드리지 않도록 전용 이름·kubeconfig·소유권 확인을 사용하며, 기본 kubectl 컨텍스트는 바꾸지 않습니다.
소유권을 확인할 수 없는 클러스터는 재사용하거나 삭제하지 않습니다.
