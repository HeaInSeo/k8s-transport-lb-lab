# 코드 없이 이해하기

## 이번에 알아볼 질문

서버를 3개 띄웠는데 왜 한 서버만 일할까? 그리고 어떻게 여러 서버에 일을 나눌까?
이 실험실은 이것을 네 장의 결과 카드로 보여준다.

## 먼저 용어 세 개만

**kind**는 내 컴퓨터 안에 작은 Kubernetes 연습장을 만들어 준다.
**kindnetd**는 그 연습장 안에서 Pod들이 통신하도록 네트워크 길을 구성한다. 부하를 만들어 주는 도구가 아니다.
**Service**는 서버 Pod들을 찾는 입구다. 기본 Service 경로는 HTTP 요청 하나하나가 아니라 TCP 연결을 기준으로 다뤄진다.

## 전화 연결로 생각하면 쉽다

새로 전화를 걸 때마다 3명의 상담원 중 누군가에게 연결해 준다고 생각하자.
전화 한 통을 유지하며 질문을 600번 하면 상담원이 바뀌지 않는다.
HTTP도 연결을 계속 재사용하면 이와 비슷하다. gRPC는 한 연결에서 여러 호출을 보낼 수 있으므로 같은 문제가 보인다.

Headless + round_robin에서는 클라이언트가 상담원 3명의 번호를 알고 각각 연결한 뒤 질문할 때마다 상대를 선택한다.
이때 gRPC ClientConn이라는 논리적인 객체 하나가 여러 실제 TCP 연결을 관리한다.
이 비유는 단항 호출의 선택을 설명한다. 이미 시작한 긴 스트림을 중간에 다른 서버로 옮긴다는 뜻은 아니다.

## 보고서 읽는 순서

첫 카드: HTTP가 새 연결을 만들 때 요청이 여러 Pod에 가는지 본다.
두 번째 카드: 같은 HTTP라도 연결을 재사용하면 한 Pod로 모이는지 본다.
세 번째 카드: 기본 gRPC에서도 한 Pod로 모이는지 본다.
네 번째 카드: Headless + round_robin을 쓸 때 다시 여러 Pod가 일하는지 본다.

PASS는 '해당 실험이 기대한 현상을 실제로 관찰했다'는 뜻이다. 모든 카드가 균등 분산되었다는 뜻이 아니다.
FAIL이면 오류 샘플과 환경 검증을 먼저 읽는다. 준비 실패, Pod 재시작, 연결 재생성도 결과에 영향을 준다.

## 지금 하지 않는 판단

이 숫자로 'HTTP가 더 빠르다', 'gRPC가 더 빠르다', '운영에서도 이 처리량이 나온다'고 결론 내리지 않는다.
실험은 작은 메시지, 한 클라이언트의 순차 호출, 로컬 컨테이너 노드로 구성된다. 실제 서비스의 처리 시간·동시성·네트워크와 다르다.
특정 CNI가 없어도 요청 단위 분산 경로를 만들 수 있다는 기초 확인이다. 자동으로 Cilium 장애를 감지해 폴백하는 기능을 구현한 것은 아니다.
